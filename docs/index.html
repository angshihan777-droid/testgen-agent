运作流程

6 节点 LangGraph 状态图，随左侧执行过程同步高亮

1analyze · 静态分析
用 AST 提取函数、分支提示与源码哈希
↓
2generate · 生成/修正测试
根据源码、分支提示和上一轮失败生成 pytest 测试
↓
3·4execute · 隔离执行 + 变异
在临时工作空间运行 pytest --cov，校验源码完整性并执行变异测试
↓
5evaluate · 门禁与辅助归因
结合失败类型、覆盖率和变异结果决定重试、审核或结束
retry ↺ 回到生成 review ⏸ 人工确认 done ✓ 收敛
↑ 条件路由让 Agent 根据工具反馈选择下一步，而不是固定执行脚本
↓
6report · 量化报告
汇总覆盖率变化、变异杀伤、人工决定与门禁结果

为什么需要 Agent

测试代码不是“生成出来”就结束，真正困难的是执行验证、失败修正和质量判断

一次性调用 LLM

只负责生成，结果缺少验证

  • 生成后直接返回，无法保证测试可以运行
  • 覆盖率提高，不代表断言真正覆盖了业务逻辑
  • 遇到导入、语法或断言错误时需要人工修改
  • 让模型评价自己的输出，缺少确定性证据
testgen-agent

让模型生成，让工具验证

  • 调用 pytest 和 Coverage 在真实环境中执行测试
  • 读取失败堆栈并反馈给模型进行下一轮修正
  • 通过变异测试检查用例能否发现逻辑变化
  • 在高不确定性问题上暂停并请求人工确认

Agent 如何做出决策

共享状态承载上下文，确定性工具产生执行事实，evaluate 节点统一完成路由判断

AgentState · 状态输入
源码上下文 source_code · functions · source_hash
执行与质量信号 last_run · failures · coverage · mutation
循环与人工状态 attempt · max_attempts · pending_review
↓ decision node

evaluate

读取共享状态与工具事实
统一完成门禁和路由判断

↓
条件路由 · 下一步
retry 执行失败或覆盖率未达标，携带反馈回到 generate。
review 疑似源码缺陷触发 interrupt，等待人工确认后恢复。
done 质量门禁通过或达到尝试上限，进入 report。

核心能力

LLM 负责生成候选测试，关键门禁信号由真实执行和确定性工具提供

🔁

执行反馈自修正

生成测试后真实运行，将错误类型、失败信息和覆盖率反馈给下一轮生成，而不是一次性返回结果。

🧬

测试有效性验证

对源码注入比较运算符变异并重新运行测试，以变异体杀伤情况衡量用例对逻辑变化的敏感度。

🐛

疑似缺陷辅助归因

综合断言失败与变异结果生成缺陷证据，将不确定结论交给人工确认，避免直接把测试失败等同于源码错误。

🔒

隔离执行与完整性校验

在临时工作空间中执行生成测试，并通过运行前后的 SHA-256 哈希检测源码是否被修改。

✋

Human-in-the-loop

使用 interrupt 与 checkpointer 暂停工作流、保存状态并接收人工决定，其余可确定步骤自动执行。

🔌

CLI 与 MCP 接入

既可通过命令行独立运行，也可作为 MCP 工具接入 Codex、Claude 等上层 Agent 工作流。

快速开始

几条命令即可复现内置案例；没有模型密钥时也能使用确定性生成器跑通闭环

$ pip install -r requirements.txt
$ pip install -e .

$ testgen-agent run \
    --source examples/src/calc.py \
    --test examples/tests/test_calc.py \
    --target 80
⚙️

可复现运行

配置 OPENAI_API_KEY 后调用真实模型；未配置时自动使用内置确定性生成器，便于本地验证工作流。

当前边界

项目当前定位为可运行的 MVP，明确能力边界比夸大自动化程度更重要

  • 目前主要面向 Python 单文件测试生成，尚未覆盖大型多模块仓库的依赖分析。
  • 变异算子以比较运算符替换为主，后续可扩展常量、布尔条件与算术运算变异。
  • 执行隔离基于临时工作空间和源码完整性校验，尚未提供容器级安全隔离与资源限制。
  • 源码缺陷识别属于辅助归因，高不确定性结论必须经过 Human-in-the-loop 确认。
  • QuixBugs 对照评测正在完善，当前页面仅展示可复现的内置案例结果。
